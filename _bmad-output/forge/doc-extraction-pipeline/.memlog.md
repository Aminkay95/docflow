- (decision) Output contract: cloud deployment emits one standard JSON programmatically to client; on-premise deployment maps JSON to the individual client's ERP needs
- (crack) On-prem + per-client ERP mapping creates a second product (integration/services business with on-prem installs), and on-prem buyers typically forbid egress to OpenAI, forcing a second inference stack
- (note) ICM = Interpretable Context Methodology (Van Clief, 2026) / Model Workspace Protocol: folder structure as agent architecture, markdown stages, local scripts for mechanical work, human checkpoints. Model-agnostic. Distinct from MCP.
- (crack) ICM is designed for human-reviewed sequential content workflows; a high-throughput transactional extraction pipeline is the opposite workload. Use ICM for authoring prompt/schema artifacts, not as the runtime orchestrator
- (lock) Cloud-first. On-prem is designed for but not built: provider interface behind every model call so the inference stack is swappable; no on-prem work until a signed deal requires it
- (lock) Cloud tier emits one standard JSON contract to all clients; per-client ERP mapping is a deterministic config-driven layer, never prompts, never per-client code
- (crack) Pipeline is file-centric (file -> classify -> extract -> JSON) but the domain is shipment-centric; files != documents != shipments. Needs page-level segmentation below and a job/shipment aggregate above
- (direction) Reframe the classifier as a page-level segmenter rather than a file-level labeler, which makes it worth having instead of a redundant hop
- (crack) User chose 'build for all scenarios' instead of answering the granularity question: risk of designing for hypothetical edge cases. Unresolved: is a file ever multi-doctype, is a shipment ever multi-file
- (assumption) Working assumption (unconfirmed): files contain multiple doctypes and shipments span multiple files
- (lock) v1 refuses batch intake loudly: one job per intake, one shipment per job. Multi-shipment containers return 'contains N shipments, split and resubmit'. Everything else (multi-doctype files, multi-file jobs, duplicates, large scans) is handled by the universal data model
- (lock) Data model: Job -> SourceFile -> Page -> Segment(page_range, doctype, confidence) -> Document -> Extraction(fields + per-field confidence + bbox provenance) -> Mapping(per-client, deterministic config). File is a container, page is the atom, shipment is the aggregate
- (lock) Segmenter always runs on every file, never conditionally. Cheap relative to extraction; acts as the safety net
- (lock) Gate design: auto-post decided by deterministic Tier-1 checks (check digits, arithmetic, structural validity, cross-document equality, temporal ordering, referential integrity) plus Tier-2 falsifiable signals (text-layer vs vision reader disagreement, per-client historical distributions, expected-field presence). Model confidence and logprobs used ONLY for queue ordering, never for the post gate
- (lock) Trust ramp per (client, supplier, doctype, template fingerprint): UNSEEN/OBSERVED = 100% review, TRUSTED = permanent random sampling (client-visible setting). Any human correction demotes; new template resets to UNSEEN. Permanent sample doubles as the continuous eval harness
- (decision) Build order: commercial invoice first (volume + richest arithmetic invariants), then remaining types; all 7 covered by end of project
- (lock) Cloud platform is ERP-agnostic and emits one canonical JSON. Per-ERP compatibility is a SEPARATE platform for the on-prem case (converts canonical JSON into whatever the client DB expects). That second platform is explicitly deferred
- (assumption) Document set (proforma invoice, bill of lading, invoice, delivery order, port pass, custom entry, verification memo) looks like Indonesian container import documentation, implying CEISA/INSW + Inaportnet as the real national integration targets. Unconfirmed
- (crack) ERP-agnostic output has no named consumer in v1, so the canonical schema is unfalsifiable and will drift toward either a lowest-common-denominator blob or an unused superset. Needs a reference consumer
- (kill) Indonesia inference was wrong: market is Kenya. Corrected target systems: KRA iCMS (customs declaration), Kenya TradeNet / KenTrade (single window, IDF), KPA Mombasa / KWATOS (port pass, delivery order)
- (lock) Adopt standard spines rather than inventing a canonical schema: UBL/Peppol for invoice family, WCO Data Model for custom entry. Thin proprietary extension block for local document types. National code is a field in the schema, never baked into field names (so the model is not Kenya-locked)
- (lock) Foundational assumption: the field schema is invariant across document layouts; only the layout-to-field mapping varies. This is why schema-first extraction beats template-based IDP
- (crack) Field invariance is not semantic invariance. Invoice total is not customs value: Kenyan duty is assessed on CIF while invoices are often FOB. Emitting invoice_total as a customs value silently produces wrong duty
- (direction) Custom entry is the only document containing derived values (duty, VAT, IDF, RDL). It therefore closes an arithmetic loop across the whole job and is the strongest Tier-1 reconciliation check available
- (lock) Values are never computed and output as data. Document is authoritative: totals, CIF, duty all come off the paper as stated. Platform does not compute duty (deferred, liability stays with the licensed agent). Consequence: emit CIF components + incoterm explicitly rather than a derived CIF field
- (lock) Arithmetic is permitted only as a test oracle, never as an output. Two separate dataflows: extraction writes provenance-backed stated values; validation computes checks solely to decide auto-post vs review
- (crack) 'Whatever the paper says' is undefined when two documents in the same job disagree on the same field. Needs explicit per-field precedence rules and a conflict list. Also unresolved: is canonical output per-document or per-job
- (lock) Canonical output is per-document JSON, not merged per-job. Rationale: the client ERP exposes seven document-creation APIs, so the output shape matches the consumer's API shape. Each document JSON must still carry stable job id + sibling cross-references so the ERP can link them
- (lock) Field disagreement across documents routes the job to the review queue on the platform, with email notification. Same behaviour cloud and on-prem
- (lock) Goal statement: deliver trust and correct values. Computed arithmetic is checks only; emitted values are always as-stated on the paper
- (crack) Per-document posting into seven ERP APIs creates partial-posting risk: documents posted as extracted can contradict a document extracted 60s later, and referential dependencies between the seven APIs mean arbitrary order can fail mid-job. Needs job-level commit + idempotency keys
- (crack) Review queue currently conflates two different jobs: extraction review (did we read the page right) vs conflict review (the paper itself disagrees). Different owners, different fixes, different SLAs
- (lock) Posting is gated on intake completion: hold until every document in the triggering email has finished extracting, then run the gate and commit
- (crack) The email is not the job either. Trade documents arrive progressively across many emails over days/weeks (proforma first, invoice, then B/L, then delivery order and port pass). Gating on email-completion means cross-document reconciliation only ever fires on whatever happened to travel in one email
- (crack) Intake-completion hold has no escape hatch: one unreadable or rejected document (bad scan, refused batch) blocks the whole shipment indefinitely. Needs timeout plus partial-release policy
- (decision) BL number is the intended primary tracking reference for attaching later-arriving documents to a job
- (crack) BL fails as a universal key in two ways: (a) proforma invoice and often commercial invoice are issued before any BL exists, so the earliest document cannot be keyed on it; (b) consolidated LCL cargo has one master BL covering several house BLs / consignees, so BL is not unique at job granularity
- (direction) Job id should be internal and stable; external references (BL, invoice no, PO, container) are claims accumulated into a reference table used for matching, not a single primary key
- (crack) Merging two jobs after documents have posted requires correcting the client ERP. Merges must therefore resolve before commit, which means the hold boundary is 'job unresolved', not 'intake fully extracted'
- (crack) Contradiction: user asserts relations are out of scope, but already decided that field disagreement between documents routes the job to review. Detecting disagreement is by definition a cross-document relation
- (direction) Resolution: relations are INPUT, not inference. Caller asserts the grouping (job_ref / BL assertion); platform never infers or matches. Removes the job-assembly problem entirely while preserving cross-document validation
- (assumption) User states every document is tied to a bill of lading. Treated as a caller-supplied assertion rather than something the platform discovers
