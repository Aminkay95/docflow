Forge Report  ·  Idea Pressure Test

Kenyan Trade-Document Extraction API

Group in, per-document JSON out, with the trust gate that decides a human never looks at it.

Idea survives — decisions locked, one class of risk unmeasured

The pipeline shape you opened with was sound but pointed at the wrong unit of work. Over the session it moved from file → classify → extract → post to caller-grouped set → segment pages → extract stated values with provenance → validate deterministically → per-document JSON plus a conflict report. The biggest single change: the platform stopped trying to infer which documents belong together. That deleted the hardest problem in the design.

What got locked

Boundary

  • Cloud first; on-prem designed for, not built. Provider adapter behind every model call.
  • Group in, per-document JSON out. Caller asserts the grouping — the platform never matches.
  • v1 refuses multi-shipment containers loudly.
  • Seven document types covered by end of project; automation ordered by volume × determinism, B/L last.

Truth

  • Values are as-stated on the page. Arithmetic is a test oracle, never an output.
  • No duty, no CIF computation — incoterm plus components, so nobody guesses.
  • Provenance bbox mandatory on every emitted field.
  • Two review queues: we misread, versus the papers genuinely disagree.

Gate

  • Auto-post decided by deterministic checks and falsifiable signals.
  • Model confidence ranks the queue; it never gates.
  • Trust ramp per client/supplier/doctype/template, with a permanent client-visible random sample.
  • The sample is the eval harness — accuracy regressions surface without anyone arguing about thresholds.

Structure

  • File is a container, page is the atom, segment is the unit of extraction.
  • Standard spines: UBL/Peppol for invoices, WCO Data Model for customs, thin local block.
  • National code is a field, never baked into field names.
  • Schema invariant across layouts — the assumption the product rests on.

Rejected — and the reason it stays rejected

OptionWhy it died
File-level classifierA misroute feeds the wrong prompt and returns confidently wrong JSON. Silent corruption, not an error.
Batch of 5 for throughputLatency multiplier, not throughput. Queue plus concurrency limit does the job.
ICM as the runtimeICM is a human-checkpointed content workflow. Fine for prompt and schema artifacts; wrong engine for transactional extraction.
Per-client ERP mapping as promptsUnmaintainable past a handful of clients. Config-driven, and deferred to the on-prem platform.
Model confidence as the gateUncalibrated, and it drifts silently every time the model or prompt changes.
Merged per-job JSONThe ERP has seven document APIs and a customs officer will ask which document a number came from.
B/L number as the primary keyDoesn't exist when the proforma is issued; not unique for LCL cargo where one master B/L covers many house B/Ls.
Cross-email job matchingDeleted entirely by making grouping an input instead of an inference.
PaddleOCR in the cloud pathVision model is better there. PaddleOCR belongs to the on-prem stack, if it ever gets built.

What survived scrutiny

The honest weak points

  • No eval set. Accuracy on stamps, handwriting, rotated scans and merged table cells is unmeasured. Every model choice in this document is unverifiable until that exists.
  • Review rate unknown. It is the business model. A document that costs three cents and four minutes of a clerk is a two-dollar document.
  • The strongest check is the weakest link. Text-layer versus vision disagreement only works on digital PDFs. Pure scans fall back to arithmetic alone.
  • Kenyan specifics unverified. IDF/RDL/VAT treatment, iCMS required fields, TradeNet message schemas, where the port pass actually originates.
  • "Accommodate everything" has no stopping rule. A group of one is a group, so the API shape scales — but nothing here says what you decline next.

Do first

  1. Build a labelled eval set before choosing any model: 20–30 real documents per type, from a working clearing agent.
  2. Confirm with that agent: required iCMS/TradeNet fields, IDF/RDL/VAT treatment, port-pass origin, and the posting order of the seven ERP APIs.
